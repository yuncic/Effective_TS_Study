# 아이템4 - 구조적 타이핑에 익숙해지기

JS는 본질적으로 **덕 타이핑** 기반이다.
만약 어떠한 함수의 매개변수 값이 모두 제대로 주어진다면, 그 값이 어떻게 만들어졌는지 신경쓰지 않고 사용한다.

> 덕 타이핑(Duck Typing)은 프로그래밍에서 객체의 이름이나 상속 관계가 아니라, 오직 그 객체가 가진 속성과 메서드(구조)에 따라 타입을 판단하는 방식을 말합니다.
> 이름의 유래는 유명한 '오리 판정법(Duck Test)'에서 왔습니다.
> "만약 어떤 새가 오리처럼 걷고, 오리처럼 꽥꽥 소리를 낸다면, 나는 그 새를 오리라고 부를 것이다."

TS는 이러한 동작, 즉 매개변수 값이 요구 사항을 만족한다면 타입이 무엇인지 신경 쓰지 안흔 동작을 그대로 모델링한다.
그런데 타입 체커의 타입에 대한 이해도가 사람과 조금 다르기 때문에 가끔 예상치 못한 결과가 나오기도 한다.

물리 라이브러리와 2D 벡터 타입을 다루는 경우를 가정해보자.

```ts
interface Vector2D {
  x: number;
  y: number;
}
```

벡터의 길이를 계산하는 함수는 다음과 같다.

```ts
function calculateLength(v: Vector2D) {
  return Math.sqrt(v.x ** 2 + v.y ** 2);
}
```

이제 이름이 들어간 벡터를 추가한다.

```ts
interface NamedVector {
  name: string;
  x: number;
  y: number;
}
```

NamedVector는 number 타입의 x와 y속성이 있기 때문에 calculateLength 함수로 호출이 가능하다.

```ts
const v: NamedVector = { x: 3, y: 4, name: "Pythagoras" };
calculateLength(v); //정상 결과는 5
```

calculateLength 함수의 매개변수는 x: number, y: number 타입을 받는다. (Vector2D)
하지만 name: string이 추가된 NamedVector 타입을 매개변수로 받아도 에러가 터지지 않는다.
필요한 요건(x,y)이 다 채워져 있으므로 통과시킨다.

> 핵심은 "최소한의 조건만 만족하면 합격!"

다음으로 3D 벡터를 만들어 보겠다.

```ts
interface Vector3D {
  x: number;
  y: number;
  z: number;
}
```

```ts
function normalize(v: Vector3D) {
  const length = calculateLength(v);
  return {
    x: v.x,
    y: v.y,
    z: v.z,
  };
}
```

calculateLength 함수의 연산에는 z가 없음에도 불구하고 normalize 함수는 에러없이 실행이 된다.
구조적 타이핑 관점에서 최소 조건인 x,y가 있기 때문에 Vector2D와 호환된다.
따라서 오류가 발생하지 않았고, 타입 체커가 문제로 인식하지 않았다.

함수를 작성할 때, 호출에 사용되는 매개변수의 속성들이 매개변수의 타입에 선언된 속성만을 가질 것이라 생각하기 쉽다.
이러한 타입을 닫힌(closed), 봉인된(sealed) 또는 정확한(precise) 타입이라고 부르며, TS의 타입 시스템에서는 표현할 수 없다.
좋든 싫든 타입은 열려있다.
이러한 특성 때문에 가끔 당황스러운 결과가 발생한다.

```ts
function calculateLengthL1(v: Vector3D) {
  let length = 0;
  for (const axis of Object.keys(v)) {
    const coord = v[axis];
    // ~~~'string'은 'Vector3D'의 인덱스로 사용할 수 없기에
    //     엘리먼트는 암시적으로 'any' 타입입니다.
    length += Math.abs(coord);
  }
  return length;
}
```

axis는 Vector3D 타입인 v의 키 중 하나이기 때문에 "x", "y", "z" 중 하나여야 합니다.
그리고 Vector3D의 선언에 따르면, 이들은 모두 number 타입 이므로 coord의 타입이 number가 되어야한다고 예상할 수 있지만, 아니다.

앞에서 Vector3D는 봉인(다른 속성이 없음)되었다고 가정했다.
그런데 다음 코드처럼 작성할 수도 있다.

```ts
const vec3D = { x: 3, y: 4, z: 1, address: "123 Broadway" };
calculateLengthL1(vec3D); //정상, NaN을 반환한다.
```

v는 어떠한 속성이든 가질 수 있기 때문에 axis의 타입은 string이 될 수도 있다.
그러므로 앞서 본 것처럼 TS는 v[axis]가 어떠한 속성이 될지 알 수 없기 때문에 number라고 확신할 수 없다.

```ts
class SmallNUmmContainer {
  num: number;
  constructor(num: number) {
    if (num < 0 || num >= 10) {
      throw new Error("error");
    }
    this.num = num;
  }
}

const a = new SmallNumContainer(5);
const b: SmallNumContainer = { num: 2024 }; //정상
```

이걸 const b 가 통과하는 이유는 TS의 구조적 타이핑 특성 때문이다.

`SmallNumContainer` 클래스는 컴파일(타입 검사) 시점에 다음과 같은 모양(인터페이스)으로 변환된다.
대입한 `{num : 2024}` 객체 역시 num이라는 숫자를 가지고 있으므로, TS가 보기에는 `SmallNumContainer`가 요구하는 모양과 일치한다.
그리고 생성자의 검증 로직은 런타임에만 작동한다.
if문 코드는 생성자(constructor)내부에 들어있다.
생성자는 반드시 `new SmallNumContainer` 로 객체를 생성할 때만 실행되는 코드이다.
하지만 b를 만들 때는 new를 쓰지 않고 객체 리터럴을 그냥 갖다 꽂았기 때문에, 생성자 함수 자체를 호출한 적이 없다.
그렇기에 b가 그냥 통과된다.

테스트를 작성할 때는 구조적 타이핑이 유리하다.
데이터베이스에 쿼리하고 결과를 처리하는 함수를 가정해보자.

```ts
interface Author {
  first: string;
  last: string;
}

function getAuthors(database: PostgresDB): Author[] {
  const authorRows = database.runQuery("SELECT first, last FROM authors");
  return authorRows.map((row) => ({ first: row[0], last: row[1] }));
}
```

`getAuthors`함수를 테스트하기 위해서는 모킹한 PostgresDB를 생성해야한다.
그러나 구조적 타이핑을 활용해서 더 구체적인 인터페이스를 구축하는 방법이 더 낫다.

```ts
interface Author {
  first: string;
  last: string;
}

interface DB {
  runQuery: (sql: string) => any[];
}

function getAuthors(database: DB): Author[] {
  const authorRows = database.runQuery("SELECT first, last FROM authors");
  return authorsRow.map((row) => ({ first: row[0], last: row[1] }));
}
```

`runQuery` 메서드가 있기 때문에 실제 환경에서도 `getAuthors`에 `PostgresDB`를 사용할 수 있다.
구조적 타이핑 덕분에, PostgresDB가 DB인터페이스를 구현하는지 명확히 선언할 필요가 없다.

쉽게 설명하자면,

만약 이 함수를 테스트하려면, 실제 데이터베이스 연결을 맺거나, 그 복잡한 PostgresDB 객체의 모든 무거운 메서드(연결, 종료, 트랜잭션 등)를 전부 흉내 낸 가짜 객체(Mock)를 만들어야 한다. (테스트 코드가 엄청 복잡해짐)

그러나 두 번째 예제처럼 DB인터페이스를 정의함으로써,
`getAuthor`함수는 이제 거대한 `PostgresDB`를 요구하지 않고 "`runQuery`메서드만 가지고 있으면 누구든 오케이!" 라고 기준을 확 낮췄다.

테스트를 하면 이제 이렇게 하면 된다.

```ts
// 테스트용 가짜 DB (implements DB 안 써도 모양만 맞으니 통과!)
const fakeDB = {
  runQuery: (sql: string) => [
    ["John", "Doe"],
    ["Jane", "Doe"],
  ],
};

// 정상 작동!
const authors = getAuthors(fakeDB);
```

TS는 테스트 DB가 해당 인터페이스를 충족하는지 확인한다.
그리고 테스트 코드에는 실제 환경의 DB에 대한 정보가 불필요하다. 모킹 라이브러리도 필요없다.
추상화(DB)를 함으로써 로직과 테스트를 특정한 구현(PostgresDB)로부터 분리했다.

## 요약

- JS가 덕 타이핑 기반이고 TS가 이를 모델링하기 위해 구조적 타이핑을 사용함을 이해해야 한다. 어떠한 인터페이스에 할당 가능한 값이라면 타입 선언에 명시적으로 나열된 속성들을 가지고 있을 것이다.

- 클래스 역시 구조적 타이핑 규칙을 따른다는 사실을 명심해야 한다. 클래스의 인스턴스가 예상과 다를 수 있다.

- 구조적 타이핑을 사용하면 유닛 테스트를 손쉽게 할 수 있다.
